# quent vs OpenTelemetry vs tracing throughput benchmark

See [PERFORMANCE_EXPERIMENT_REPORT.md](PERFORMANCE_EXPERIMENT_REPORT.md) for the
experiment history, conclusions, and dependency-ordered plan for replaying each
optimization independently over upstream `main`.

Throughput comparison of quent's instrumentation against the OpenTelemetry 0.32
Rust SDK and `tracing`, each exercised as it is natively built. Each cell spams a
fixed number of operations (one op = one log or one span) as fast as possible
across the producer threads, then reports offered, delivered, latency/drain, loss,
and logical write-rate metrics:

Quent is measured in two forms: generated static schemas
(`quent-static-*`) and the opt-in dynamic attribute container
(`quent-dynamic-*`). The schemas are generated by `quent-instrumentation-build`
from `model.yaml`; the benchmark does not use the obsolete model macros.

The supported attribute counts are 0, 1, 2, 4, 8, 16, 32, and 64. Payloads are
deterministic and mix strings, i64, f64, bool, and primitive arrays of each type.
String lengths vary from 1 to 8,191 bytes; array lengths vary from 0 to 32, and
strings inside arrays vary from 1 to 127 bytes. All libraries receive the same
logical values. OpenTelemetry carries arrays as native array/list values. Quent
serializes typed lists natively. `tracing` has no typed array field API, so its
arrays use its standard `Debug` field representation.

- **offered** — the raw API-call rate: ops / emit time.
- **throughput** — the sustained rate. quent and the `tracing` file comparison
  are lossless, so this is ops divided by the full time to deliver everything.
  OpenTelemetry uses its native lossy bounded queue, so its result is goodput:
  what actually reached the sink, with the rest dropped.
- **write throughput** — logical bytes in the completed filesystem outputs
  divided by the same full drained interval. Files are flushed but not fsynced;
  short runs may measure page-cache bandwidth, while sufficiently large runs
  can expose dirty-page throttling and the storage ceiling.

`offered > throughput` means the caller outran an asynchronous pipeline. quent
drains its queue, `tracing` applies backpressure and drains, and OTel may drop.

Not part of default builds: the crate is a workspace member but excluded from
`default-members`, so its OpenTelemetry deps never touch a normal `cargo build`.

## Backends (native to each library)

- quent: `noop`, `raw`, `bitcode`, `ndjson`, `msgpack`, `postcard`
  (filesystem), `grpc` (collector). `raw` is the throughput-oriented native
  schema path: fixed-width little-endian Bincode with producer-local batches,
  no compression, and a bounded lossless byte handoff. `bitcode` is the compact
  column-oriented alternative.
- OpenTelemetry: `noop`, `grpc` (OTLP). No file exporter ships with OTel.
- tracing: `file` (JSON via a bounded off-thread appender with lossless
  backpressure).

gRPC/OTLP variants stream to a live in-process receiver; the tracing writer counts
newlines and resets its temporary file only after each repetition fully drains.
`noop` discards everything (caller floor only).

## Run

Real loopback sockets are required (in-process gRPC receivers), so run it in a
normal shell, not a sandbox.

```sh
BENCH_ATTRS=0,1,2,4,8,16,32,64 BENCH_THREADS=1,4,16 BENCH_OPS=2000000 \
  BENCH_CSV=target/analysis.csv BENCH_JSON=target/analysis.json \
  pixi run cargo run -p quent-bench --release
```

Knobs (env vars):

| var | default | meaning |
|--|--|--|
| `BENCH_OPS` | `2000000` | operations spammed per cell |
| `BENCH_ATTRS` | `0,1,2,4,8,16,32,64` | attribute counts to sweep (comma list) |
| `BENCH_THREADS` | `1,4,8` | producer thread counts to sweep (comma list) |
| `BENCH_REPS` | `1` | repetitions averaged per cell |
| `BENCH_VARIANTS` | (unset) | exact variant labels to run (comma list) |
| `BENCH_CSV` | (unset) | if set, write raw results to this CSV path |
| `BENCH_JSON` | (unset) | if set, write self-describing JSON (units + metric semantics) to this path |
| `QUENT_EVENT_CHANNEL_CAPACITY` | `4096` | maximum queued Quent events before lossless producer backpressure |

The table (stdout) reports `offered/s`, `tput/s`, `loss%` per variant, plus a
PEAK summary across the thread sweep; live progress goes to stderr.

## Plot

With `BENCH_CSV` set, plot operation-throughput, latency, and logical
write-throughput figures. The operation-throughput figure
is a grid of (attributes x threads) cells, each split into achieved and offered
panels, with bars colored by library and the dropped fraction overlaid in gray:

```sh
pixi run uv run --with matplotlib \
  bench/plot.py target/analysis.csv plots/analysis.png
# also writes plots/analysis-latency.png
# and plots/analysis-write.png
```
