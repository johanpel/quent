# Quent exporter performance experiment

## Status and scope

This report records the exporter and benchmark work performed on
`bench-vs-otel-bitcode` through commit `491791a`, the uncommitted experimental
working tree on 2026-07-21, and the subsequent 14-candidate isolated replay over
the latest fetched upstream `main` on 2026-07-22. The original branch analysis
used `origin/main` at `c0d3781`; the isolated replay used upstream
`f884b337b9108f6fb06af28d0f9c7c9d852df4a3`.

The report covers the performance-related changes only. The original branch
history also contains merges from upstream and unrelated FSM/resource work
inherited through those merges. None of the isolated candidates has landed on
upstream or been combined into the original branch; their commits exist only on
the temporary experimental branches listed below.

The main conclusion is:

> Quent's largest problem at the high-payload/high-concurrency point was not the
> intrinsic cost of binary encoding. It was allowing allocation-heavy event
> objects to accumulate, move between threads, and remain alive until a shared
> consumer serialized and destroyed them. Bounding the pipeline and moving raw
> encoding into producer-local byte batches made the largest difference.

The final focused branch grid made the Quent `raw` variants faster than the
corresponding lossless tracing file variants in every tested `(attributes,
threads, signal)` cell for 0, 8, and 64 attributes and 1, 4, and 16 producer
threads. The later isolated replay showed which parts caused that result:
producer-side serialization and local byte batching were decisive; changing to
raw Bincode alone was not. These remain experimental results from one machine,
not general claims about all workloads or storage devices.

## What the benchmark measures

Each cell emits a fixed number of log or span operations as quickly as possible.
The benchmark now reports several different concepts intentionally:

- **Offered throughput** is operations divided by producer emission time. It
  measures how quickly callers can submit work.
- **Delivered throughput** is operations that reached the sink divided by the
  complete interval, including final pipeline drain. For lossless Quent and
  tracing file variants, all offered operations must be delivered.
- **Caller p50/p95/p99** are sampled durations of individual API calls while the
  producers are under load. Backpressure appears here.
- **Pipeline drain** is the time between the last producer operation and complete
  pipeline shutdown/flush. It measures the backlog left behind when producers
  finish; it is not per-event latency.
- **Logical write throughput** is completed file bytes divided by the same full
  drained interval. Files are flushed but not `fsync`ed.
- **Loss** is the fraction of operations not counted at the sink. Every counted
  Quent result is required to have zero loss.

Logs and spans remain separate. A span has lifecycle semantics and emits both
boundaries in the file comparison, so it should not be interpreted as equivalent
to one log record.

## Fair workload semantics

### The first workload was misleading

The original comparison placed all benchmark attributes in Quent's dynamic
attribute container. That exercised a valid fallback API, but it did not
represent Quent's intended primary use: generated, typed schemas. At 64
attributes and 16 threads, tracing JSON could therefore appear faster than
Quent's binary exporters.

That result did **not** establish that string formatting is inherently faster
than binary encoding. It established that the tested Quent path was dominated by
dynamic value construction, allocation ownership, queueing, copying, shared
batching, and memory bandwidth.

### Static and dynamic are now distinct variants

The benchmark now has separately labeled generated-static and dynamic Quent
variants. Static schemas are generated by `quent-instrumentation-build` from
`bench/model.yaml`; the obsolete model crates/macros are no longer used to define
the benchmark model.

Schemas exist for 0, 1, 2, 4, 8, 16, 32, and 64 attributes. Payloads use a
deterministic mixture supported by all compared libraries:

- strings with lengths from 1 through 8,191 bytes;
- signed integers, floating-point values, and booleans;
- primitive arrays of strings, integers, floats, and booleans;
- arrays with lengths from 0 through 32;
- strings inside arrays with lengths from 1 through 127 bytes.

Quent and OpenTelemetry retain typed array/list values. Tracing has no typed
array field API, so arrays use tracing's normal `Debug` field representation.
This limitation is disclosed rather than silently changing the logical values.

The dynamic-only optimization remains available and is measured as its own
variant. It is useful for workloads that genuinely need runtime-defined fields,
but it is not allowed to stand in for Quent's generated-schema path.

## Chronology of the work

### 1. Establish a multi-library benchmark

The early branch added a configurable Quent/OpenTelemetry/tracing benchmark,
CSV output, self-describing JSON output, and plotting. It supports logs and spans,
multiple attribute counts, multiple producer counts, repetitions, file and
collector sinks, and live progress.

The benchmark distinguishes caller rate from fully delivered throughput. This
was essential: an asynchronous producer can report a very high call rate while
leaving seconds of work queued behind it or dropping most of its events.

### 2. Remove benchmark-only hot-loop costs

Commit `491791a` removed several costs that were artifacts of the harness rather
than unavoidable exporter work:

- one persistent Quent entity is created per producer thread;
- UUID creation was removed from the per-event hot loop;
- caller latency is sampled instead of timing every operation;
- final pipeline drain is measured explicitly;
- throughput and latency receive separate plots.

These changes made the comparison more representative and made it possible to
see whether a high offered rate was simply creating a large backlog.

### 3. Improve the existing shared exporters

The same committed pass improved the pre-existing paths:

- collector batches are serialized together;
- an intermediate per-event collector channel was removed;
- dynamic attribute construction performs fewer allocations;
- filesystem encoders operate on batches;
- CPU-heavy filesystem encoding is dispatched to asynchronous Rayon work;
- Msgpack, Postcard, and NDJSON gained batch-oriented handling;
- Quent paths remain lossless.

These were useful general improvements, especially away from the most extreme
payload, but they did not eliminate the central ownership problem: large typed
events could still wait in a shared queue until another thread serialized and
dropped them.

### 4. Diagnose the 64-attribute/16-thread reversal

The surprising tracing result caused us to isolate the stages rather than tune
the codec blindly. The important observations were:

1. Producers allocated strings, arrays, vectors, and event containers.
2. Sending an event moved ownership into the pipeline; it did not destroy the
   allocations.
3. An unbounded queue let producers run far ahead of serialization and I/O.
4. The consumer eventually serialized and destroyed those allocations on a
   different thread from the one that allocated them.
5. Many large live payloads increased resident memory, allocator traffic,
   cache misses, cross-thread frees, and memory-bandwidth pressure.
6. The final drain exposed how much deferred work was hidden behind the offered
   rate.

The relevant point about “the producer did not free the event” was therefore not
that Rust leaked it. Ownership was correct and the event was eventually dropped.
The problem was **when and where** destruction happened, and how many events were
alive simultaneously.

### 5. Bound the lossless Quent queue

The instrumentation event handoff changed from an unbounded queue to a bounded,
lossless queue. Its default capacity is 4,096 events and can be changed with
`QUENT_EVENT_CHANNEL_CAPACITY`.

When the queue fills, producers wait instead of growing memory without limit.
This trades some caller latency for:

- a predictable upper bound on queued event objects;
- lower peak live memory;
- less allocator and cache pressure;
- less deferred destruction;
- a smaller end-of-run drain;
- sustained throughput that reflects the consumer's real capacity.

This was one of the largest improvements. The lesson is not merely “unbounded
queues are slow”; it is that an unbounded ownership queue is especially harmful
when each item contains many independently allocated values and producers can
substantially outrun the sink.

### 6. Try a compact Bitcode exporter

A framed Bitcode filesystem exporter/importer was added. It serializes whole
batches so Bitcode can exploit column-oriented repetition across events. The
native path derives Bitcode traits and reuses encoder state; a Serde-compatible
path remains available. Encoding work can be parallelized and multiple encoded
batches can be in flight while ordered output is preserved.

Bitcode is attractive when compact output matters. In this experiment, however,
compact encoding and deferred batch processing were not the fastest possible
throughput design for large payloads. More codec work can save bytes while
consuming CPU, and retaining typed batches keeps their allocation graphs alive
until batch encoding completes.

### 7. Add the throughput-oriented `raw` path

The `raw` exporter/importer deliberately prioritizes throughput over compression
or minimal file size. Its format is a sequence of frames:

```text
[4-byte big-endian payload length][Bincode payload]
```

The Bincode payload uses fixed-width little-endian numeric encoding. Strings and
arrays retain their lengths and contents. Static events use Bincode's native
`Encode` implementation; dynamic events use the Serde-compatible Bincode path.

The names have distinct meanings:

- **Bitcode** is a compact, batch-oriented serialization codec.
- **Bincode** is the binary codec used to encode values in the raw frames.
- **Raw** is the complete throughput-oriented file format and pipeline: simple
  framing, Bincode encoding, no compression, producer-local byte batching, a
  bounded lossless byte handoff, and one ordered writer.

The decisive optimization was not just choosing Bincode. It was changing the
ownership pipeline:

1. The producer constructs the typed event.
2. It immediately encodes the event into a reusable thread-local byte batch.
3. The typed event and its strings/arrays are destroyed on that producer thread.
4. Only contiguous owned bytes cross the queue.
5. A batch is handed to the writer at 64 events or 1 MiB.
6. The bounded channel permits at most 256 byte batches in flight.
7. The single background writer writes batches in order using a 1 MiB buffer.
8. Explicit producer flush hooks ensure partial thread-local batches are not
   stranded during shutdown.

This removes the intermediate per-event object queue from the raw benchmark
path, shortens allocation lifetimes, shifts destruction back to the allocating
thread, amortizes channel synchronization, and gives the writer a simple
contiguous-byte workload.

It does not magically make dynamic attributes allocation-free. Their strings,
vectors, and tagged values still have to be constructed. It does ensure those
objects have a short, producer-local lifetime instead of accumulating downstream.

### 8. Make tracing file output lossless for the comparison

Tracing's non-blocking appender normally drops records when its bounded queue is
full. The benchmark now configures backpressure instead. The guard is retained
through the measured section and the temporary file is cleared only after each
repetition has drained.

This means the final Quent-versus-tracing file comparison is lossless on both
sides. It also explains tracing's larger high-load caller latency and final drain:
those costs can no longer be hidden as dropped records.

OpenTelemetry remains on its native bounded batch behavior and may drop. Its
throughput is therefore labeled as delivered goodput, with loss reported
separately; it must not be compared as though it were lossless.

### 9. Add byte-throughput accounting

The benchmark snapshots Quent output-directory sizes around each repetition and
uses the completed tracing file length. CSV, JSON, console output, and plotting
now expose:

- `bytes_written`: logical bytes added by the drained cell;
- `write_bytes_s`: logical bytes divided by full delivered duration.

The plotter writes a third figure alongside operation throughput and latency.
The JSON metadata explicitly states that this is not direct device telemetry.

## What made the biggest impact

In descending order of importance for the extreme file-export workload:

1. **Correct workload representation.** Separating generated static schemas from
   the dynamic fallback stopped the benchmark from treating Quent's least common
   API as its only API.
2. **Bounded lossless flow control.** Backpressure stopped allocation-heavy event
   graphs from growing without limit and made delivered throughput meaningful.
3. **Producer-side serialization.** Destroying typed payloads immediately on the
   producer eliminated long-lived cross-thread object graphs from the raw path.
4. **Producer-local byte batching.** Sending up to 64 events or 1 MiB per channel
   operation greatly reduced forwarding and synchronization overhead.
5. **A deliberately simple raw format.** Fixed-width Bincode and no compression
   favored CPU and memory throughput over compactness.
6. **Removing harness and lifecycle overhead.** Persistent entities and no
   per-event UUID construction prevented the benchmark itself from dominating.
7. **Batching existing collector/filesystem paths.** This reduced per-event
   overhead broadly, but did not by itself solve the large-payload ownership
   bottleneck.

The result argues against optimizing serialization algorithms in isolation. For
this workload, queue topology, ownership lifetime, destruction locality, batch
size, and memory bandwidth mattered at least as much as codec instruction count.

## Optimization replay and merge plan

The final working tree contains many changes at once. Its result proves that the
combined design can perform well, but it does **not** assign the total improvement
to any one patch. The clean way to upstream this work is to replay small changes
over current upstream `main`, measure each one against the same fixed harness,
and merge only changes whose benefit, correctness, and maintenance cost justify
them.

### First freeze the benchmark contract

Benchmark corrections must land in the experimental harness before testing
production optimizations, but their apparent speedups must not be credited as
runtime improvements. Freeze these semantics:

- generated static Quent and separately labeled dynamic Quent variants;
- identical deterministic mixed logical values for all libraries;
- persistent entity lifetime per producer thread;
- no UUID generation in the measured event loop;
- lossless Quent and lossless tracing file paths;
- equivalent log/span lifecycle counting;
- offered time, complete delivered time, sampled caller latency, drain, loss,
  logical bytes, and physical I/O telemetry reported separately;
- fixed operation count, repetitions, queue configuration, CPU placement, and
  machine/device state.

This frozen harness should be its own reviewable patch. Once frozen, do not edit
it between optimization candidates except to fix a demonstrated measurement bug.

### Recommended replay order

Use separate worktrees or short-lived branches rooted at the same upstream
`main`. Do not build a long stack and then try to infer which lower patch helped.

1. Apply only B1–B5 to create the fixed benchmark branch.
2. Measure upstream unchanged and archive raw CSV/JSON, machine metadata, and
   physical I/O telemetry.
3. Test P1 and P2 independently because they have narrow scopes.
4. Test P3 alone with the smallest possible reference backend, then test each of
   P4 and P5 independently on top of P3.
5. Test P6 directly over upstream with existing exporters before introducing a
   new format. Its benefit should be visible in RSS, drain, and overload behavior,
   not just operation rate.
6. Test P7 separately as a format/value proposition.
7. Add P8 as the raw-format baseline, initially retaining ordinary consumer-side
   encoding.
8. Add P9 on top of P8. This A/B isolates the central hypothesis: producer-local
   serialization and byte batching outperform forwarding allocation-heavy typed
   events.
9. Test P10 on top of P9 to determine whether maintaining native and Serde codec
   implementations is worthwhile.
10. Only after isolated tests, build combinations from the winning candidates and
    check whether their gains compose or overlap.

### Per-candidate run protocol

Each candidate should pass three gates:

1. **Screening:** a quick 0/8/64-attribute, 1/16-thread, single-repetition run to
   reject regressions and no-effect changes cheaply.
2. **Confirmation:** the full fixed grid with enough operations to reach steady
   state and at least five repetitions, reporting dispersion rather than only an
   average.
3. **Correctness and operations:** round-trip decoding, zero-loss assertions,
   ordering, clean shutdown, bounded memory, tests, formatting, Clippy, and
   failure-path behavior.

For every candidate, record:

- exact upstream commit and patch ID;
- CPU, memory, kernel, filesystem, device, Rust/Pixi versions, and temperatures;
- payload/schema hash and all benchmark environment variables;
- offered/delivered operations per second, caller percentiles, drain, RSS peak,
  allocations if available, logical B/s, physical B/s, CPU time, and output size;
- median and variability across repetitions;
- profiles from both a representative low-load cell and the 64-attribute,
  16-thread stress cell.

### Merge, hold, and drop rules

A production candidate should be merged only when it shows a repeatable material
benefit in its intended workload and does not merely move cost into unreported
latency, drain, memory, loss, file size, or shutdown work.

Suggested decision rules:

- **Merge:** clear repeatable benefit, no correctness regression, understandable
  semantics, and maintenance cost proportional to the gain.
- **Hold:** benefit exists only above a crossover point or requires operational
  tuning; keep behind an option until the use case is established.
- **Drop:** no repeatable benefit, a gain fully overlaps another simpler change,
  tail latency or memory worsens unacceptably, or complexity exceeds its value.
- **Benchmark-only:** measurement/fairness corrections B1–B6 should not be sold as
  production speedups.

In particular, Bitcode, Rayon parallelism, dual native/Serde implementations, and
format-specific batch machinery should not be upstreamed merely because they are
present in the final winning tree. They each need to win their own isolated test.
The most important experiment to reproduce first is P8 versus P9; the next is P6
over existing upstream exporters.

that the combined design can be fast, but it cannot say which edits deserve to
move to mainline. To establish that attribution, the 14 proposed changes were
implemented or audited independently from one benchmark-only baseline over the
latest fetched upstream `main`.

### Controlled measurement protocol

The fixed screening workload was 8 and 64 attributes, 1 and 16 producer
threads, 50,000 operations per cell, three repetitions, caller-latency sampling
at 1 in 1,024 operations, and `RAYON_NUM_THREADS=24`. Each candidate run included
only affected variants and an unchanged control. The baseline ran at both the
start and end of the sequence.

The root runner measured candidates one at a time with real loopback sockets
outside the restrictive sandbox. Before each run it required no Cargo, rustc,
or `quent-bench` process, package temperature at or below 50°C, and dirty plus
writeback pages below 64 MiB. It called `sync` after every candidate. The 16
successful datasets—two baselines and 14 candidates—took 1,274.6 seconds
(21 minutes 14.6 seconds). Boundary package temperatures remained between 35°C
and 38°C, and no thermal contention was observed. Intel P-state remained on the
`powersave` governor.

Start-to-end baseline geometric-mean drift was 0.988x delivered throughput,
1.053x offered throughput, 0.954x caller p99, and 1.029x drain. However,
documentation-only/no-runtime Postcard controls measured about 0.89–0.91x the
bracketing baseline. That exposes a variant-order or process-warm-up confound
larger than boundary drift; effects near 10% are therefore inconclusive unless
supported by same-run controls or consistent per-cell behavior.

### What each isolated trial established

#### 01 — Producer-side serialization and local byte batching

This candidate retained standard Postcard framing but encoded on producer
threads into reusable thread-local buffers. It moved a byte batch—not a graph of
typed values—into a bounded queue after 64 events or 1 MiB, recycled buffers,
used one ordered writer, and explicitly flushed partial thread-local batches.
Typed payloads were therefore destroyed on their allocating producer thread.

At 64 attributes and 16 threads:

| Variant | Ordinary throughput | Producer throughput | Ratio | Ordinary p99 | Producer p99 | Ordinary drain | Producer drain |
|---|---:|---:|---:|---:|---:|---:|---:|
| Static log | 121.1k/s | 314.3k/s | **2.60x** | 0.344 ms | 17.15 ms | 348 ms | 48 ms |
| Static span | 153.0k/s | 319.1k/s | **2.09x** | 0.215 ms | 5.13 ms | 276 ms | 23 ms |
| Dynamic log | 87.4k/s | 327.5k/s | **3.75x** | 0.091 ms | 12.36 ms | 507 ms | 42 ms |
| Dynamic span | 92.1k/s | 305.8k/s | **3.32x** | 0.067 ms | 7.18 ms | 467 ms | 23 ms |

At one thread, delivered throughput improved 4.02x–6.09x and caller p99 also
improved. At 16 threads, the single writer became the limiter and the bounded
byte queue deliberately exposed that limit to callers. The much shorter drain
shows that the ordinary offered rate represented substantial deferred work.

This is the decisive result, but it measures a package: producer encoding,
thread-local aggregation, bounded byte handoff, recycling, one writer, and
partial-batch flush. It does not assign causality within that package. Mainline
work should keep Postcard initially, make capacity and batch limits
configurable, propagate writer errors, audit thread-local sink identity reuse,
document backpressure semantics, and measure longer steady-state operation.

##### API directions proposed by the user

During review of these results, the user proposed exposing the performance
trade-off deliberately instead of choosing one universal observer behavior:

- Allow individual entity observers to be marked as **throughput-optimized** or
  **latency-optimized**, with a **balanced** implementation as the normal middle
  ground. A throughput-oriented observer could use larger producer-local batches
  and tolerate more buffering; a latency-oriented observer could flush smaller
  batches sooner; the balanced policy could bound both costs without maximizing
  either extreme.
- Allow users to choose an **unbounded queue** for non-blocking submission or a
  **bounded queue** for blocking/backpressure behavior. This makes the memory,
  caller-latency, and drain trade-off part of the API contract rather than an
  accidental implementation detail.

These are design proposals from the user, not outcomes already established by
the isolated measurements. They should be evaluated as explicit policy variants,
including a missing unbounded producer-byte-queue control, before defaults are
selected.

#### 02 — Bounded typed-event queue

A typed queue capacity of 4,096 reduced final drain to 12.2% of baseline and
peak RSS to about 297 MiB, versus roughly 1.4–2.2 GiB in filtered Postcard
no-op-control runs. Delivered throughput fell about 16%, offered throughput fell
70%, and caller p99 rose substantially. The 64-attribute/16-thread cells
delivered 75.6k–136.9k/s with p99 of 0.84–3.24 ms. This validates bounded memory
and honest backpressure, not a faster pipeline. Keep it only as an operational
policy or revisit byte-based capacity.

#### 03 — Consumer-side raw Bincode

Raw Serde Bincode kept the unchanged typed-event pipeline and consumer-side
encoding. Delivered throughput was effectively identical to Postcard (1.002x)
while output was 1.164x as large. Static 64-attribute/16-thread results regressed
and dynamic results were roughly neutral. A simpler codec and framing alone do
not solve the pipeline bottleneck.

#### 04 and 06 — Batching already upstream

Upstream commit `24d832ad` already had reusable observer buffers, `recv_many`,
`batch_size_hint`, and `drain_events`. Its NDJSON, MessagePack, and Postcard
filesystem exporters also already batch writes without changing format or
order. These audits prevent incorrectly attributing existing behavior to the
experimental branch.

#### 05 — Direct collector forwarding

Removing the intermediate event channel and 128 ms serializer/coalescer helped
several 8-attribute cells, sometimes by 2.13x, but regressed most 64-attribute
cells. At 64 attributes/16 threads, delivered ratios were 0.43x–0.95x and peak
RSS remained about 8 GiB. A new attempt should keep direct observer-batch
serialization while restoring size-aware request coalescing or reuse a byte
request buffer.

#### 07 — Static schemas as the primary path

This documentation-only candidate makes generated `instrumentation-build`
schemas the primary path and labels dynamic attributes as a runtime-defined
fallback. It is worth merging for guidance, but it has no runtime speed claim.

#### 08 — Dynamic allocation reductions

This trial borrowed literal keys through `Cow<'static, str>`, stored up to four
attributes inline with `SmallVec`, reserved exact larger capacities, created
dynamic values directly, and removed an intermediate boolean-vector
conversion. Dynamic noop offered rate improved 1.246x overall and 1.50x–1.73x
at 64 attributes/16 threads, but actual Postcard delivery improved only 1.027x
overall and was mixed under contention. The public `String` to `Cow` and `Vec`
to `SmallVec` field changes are source-breaking. Keep the equivalence tests and
separately evaluate non-breaking constructors, static-key APIs, exact reserve,
and direct typed-list construction.

#### 09 — Reusable codec and output buffers

NDJSON serialized directly into its persistent byte buffer. MessagePack and
Postcard reserved frame prefixes in reusable storage, serialized directly,
patched lengths, and rolled back partial output on errors. Exact legacy bytes
and ordered round trips were tested. Delivered throughput improved 1.164x
overall. One-thread cells improved 1.23x–1.44x at 8 attributes and mostly
1.11x–1.35x at 64 attributes. At 64 attributes/16 threads, dynamic variants
improved 1.05x–1.24x while static variants ranged from 0.86x to 1.11x. The
consistent one-thread benefit, compatibility, and modest scope make this the
best conventional merge candidate, subject to focused confirmation because
control noise was about 10%.

#### 10 — Native versus Serde Bincode

With fixed-width configuration, framing, allocation, locking, and writes held
constant, native Bincode produced a 1.161x geometric mean driven by
8-attribute/one-thread gains of 1.47x–1.55x. At 64 attributes/16 threads it was
0.87x for logs and 0.98x for spans. Maintaining two paths is not justified by
this result. Native derives may be revisited inside the producer-side fast path,
where queueing and contention differ.

#### 11 — Thresholded Rayon encoding

Batches of at least 128 events moved to Rayon; smaller batches encoded inline.
The normal observer batch is 256, so nearly all steady-state work paid task
scheduling and transfer costs. Overall throughput fell to 0.933x and drain rose
to 1.381x; most 64-attribute/16-thread cells delivered 0.79x–0.95x baseline.
Drop this threshold/design. A byte-based crossover would require a new isolated
test.

#### 12 — Compact Bitcode

Bitcode helped several one-thread cells but at 64 attributes/16 threads
delivered only 0.41x–0.94x Postcard throughput and increased drain. The output
was only 2.3% smaller because the workload is dominated by variable strings and
arrays. It should not be merged as a speed feature; compactness or decode
properties would need their own product requirement and measurement.

#### 13 — Flush and shutdown lifecycle

Latest upstream already uses shared observer ownership, last-drop cancellation,
ordered queue drain, a partial final batch, exactly one exporter shutdown, and
a synchronous join. The candidate added tests for 1,025 queued events, clone
lifetime, push-failure continuation, and shutdown failure. The tests are useful;
there is no runtime optimization to claim.

#### 14 — Entity and identifier lifetime

Generated handles already create one UUID in `Handle::new` and reuse it for all
events. Contexts, observers, exporters, runtimes, sidecars, and benchmark handles
are constructed outside the event hot loop. No mainline production change is
justified.

### Mainline order implied by the isolated results

1. Develop candidate 01 as an explicit producer-encoded bounded fast path,
   initially preserving Postcard compatibility. Resolve caller-latency and
   backpressure semantics before merging.
2. Confirm candidate 09 in a tighter same-process experiment, then merge its
   direct reusable encoding buffers if the benefit repeats.
3. Merge candidate 07 documentation and candidate 13 lifecycle contract tests
   as non-performance improvements.
4. Extract only non-breaking pieces from candidate 08 and measure them
   independently.
5. Use candidate 02 only when bounded memory/backpressure is the desired
   operational policy; do not advertise it as throughput work.
6. Restore size-aware aggregation before reconsidering candidate 05.
7. Do not merge candidates 03, 10, 11, or 12 for performance on this evidence.

## NVMe interpretation

The logical byte plot is useful for seeing where a sustained run plateaus, but a
short result near 5 GB/s does not prove that 5 GB/s reached the physical SSD.
Normal buffered writes can complete into the Linux page cache. The kernel may
write dirty pages to the device later.

To establish an NVMe ceiling reliably, a future run should:

- use enough operations and payload bytes to exceed transient page-cache effects;
- monitor device throughput concurrently with `iostat` or equivalent block-device
  telemetry;
- record `/proc/<pid>/io` physical write counters as a separate metric;
- optionally add an explicitly labeled `fsync`/durability mode;
- report filesystem, mount options, device model, CPU frequency/temperature, and
  competing I/O;
- keep logical exporter throughput separate from physical-device throughput.

An `fsync` mode answers a different question and should not silently replace the
current buffered-throughput benchmark.

## What this experiment does not prove

- It is not a valid before/after comparison with results from another machine.
- It does not establish durable physical NVMe throughput because output is not
  fsynced and block-device counters were not captured.
- It does not show that raw output is always the right format; Bitcode may be a
  better storage/CPU trade-off when compactness matters.
- It does not make dynamic fields free; it only gives their allocations a much
  shorter and better-localized lifetime.
- It does not justify changing production defaults solely from either the
  200,000-operation cumulative grid or the 50,000-operation isolated screen.
